the correction this phase forced

Phases 1 and 2 named Bridge as the TRY payout provider on the strength of the "Stripe's stablecoin stack" framing. That was wrong. Bridge's published route table has no TRY in either direction, so no amount of KYB approval would produce this corridor.

The honest framing is better anyway: Bridge covers the US side, which is its real product. The TRY leg is a corridor-specific partner. A stablecoin remittance app that assumed one vendor covered every destination would be a worse piece of architecture than one that planned for the opposite — because the opposite is what always happens.

Routes are a table, not a codebase

The Bridge gap stops being a defect the moment corridors are data. Adding USD→MXN is a row; it binds to a Bridge payout provider instead of the Turkish one and nothing else changes.

why this is the load-bearing decision

Every remittance business eventually discovers that no single vendor covers its destination map. The ones that hard-coded a vendor rewrite their settlement layer; the ones that put an interface there add a file. The Bridge TRY gap is the proof that this seam is doing work rather than being decorative — it was discovered during integration, and the design absorbed it without touching a screen.

contracts

Money, quotes, and the interfaces

Money is never a number

Minor units as bigint, currency-tagged, with the scale carried explicitly. The USD→USDC boundary is where the bugs live: USD has 2 decimals, USDC has 6, so every conversion crosses a factor of 10⁴ that a float would quietly corrupt. 

// money.ts
type Currency = 'USD' | 'TRY' | 'USDC';

const SCALE: Record<Currency, number> = { USD: 2, TRY: 2, USDC: 6 };

interface Money {
  readonly currency: Currency;
  readonly minor: bigint;    // $500.00 → 50_000n   ·   500.00 USDC → 500_000_000n
}

// Rates are rationals. A float rate is an unreconcilable rate.
interface Rate {
  readonly pair: 'USD/TRY';
  readonly num: bigint;      // 5284n
  readonly den: bigint;      // 100n     → 52.84
  readonly source: 'mid_market';
  readonly observedAt: string;
}

// Rescaling is explicit and total. There is no implicit coercion anywhere.
function rescale(m: Money, to: Currency): Money {
  const d = SCALE[to] - SCALE[m.currency];
  return {
    currency: to,
    minor: d >= 0 ? m.minor * 10n ** BigInt(d)
                  : m.minor / 10n ** BigInt(-d),   // caller proves divisibility
  };
}

Quotes are signed server-side

Screen 03 submits a quoteId, never amounts. The client's numbers are a rendering of the quote, never the source of it — which is what stops a stale countdown or a patched binary from reaching settlement. 

// quote.ts
interface Quote {
  readonly id: QuoteId;
  readonly corridor: CorridorId;
  readonly send: Money;          // USD 50_000n            — what the user typed
  readonly receive: Money;       // TRY 2_642_000n         — ₺26,420.00
  readonly totalCharged: Money;  // USD 50_375n            — $503.75
  readonly rate: Rate;
  readonly fees: readonly FeeLine[];
  readonly expiresAt: string;    // server clock, always
  readonly sig: string;          // HMAC over every field above
}

interface FeeLine {
  readonly kind: 'onramp' | 'network' | 'payout';
  readonly label: string;        // 'On-ramp · ACH → USDC'
  readonly amount: Money;        // USD 125n → $1.25
}

The provider interfaces

Three interfaces, each implemented once per rail. validateDestination is where Turkey's IBAN mod-97 check lives and where Mexico's CLABE check would — destination correctness is a property of the payout rail, not of the app. 

// providers/contracts.ts

interface OnrampProvider {
  readonly id: ProviderId;
  supports(rail: FiatRail): boolean;                    // 'ach' | 'wire' | 'card'
  estimateSettlement(rail: FiatRail, at: Date): Date;   // → 'arrives Wed, Aug 5'
  createDeposit(req: DepositRequest, idem: IdempotencyKey): Promise<ProviderRef>;

}

interface PayoutProvider {
  readonly id: ProviderId;
  supports(corridor: CorridorId): boolean;
  validateDestination(d: Destination): ValidationResult;  // local + synchronous
  submit(req: PayoutRequest, idem: IdempotencyKey): Promise<ProviderRef>;
  parseWebhook(raw: unknown, sig: string): PayoutEvent | null;
}

interface KycProvider {
  readonly id: ProviderId;
  createSession(userId: UserId): Promise<{ sessionId: string; uploadUrl: string }>;
  parseWebhook(raw: unknown, sig: string): KycEvent | null;
}

what parseWebhook buys

Returning null for an unrecognised or badly-signed payload — rather than throwing — makes webhook ingress total. Unknown event types from a vendor's new release get dropped and logged instead of crashing the ingress endpoint and stalling every in-flight transfer behind them. A provider shipping a feature you haven't heard of should never be an outage.

state machine

One transfer, eleven states

State is a fold over an append-only event log, not a mutable column. Three providers with three clocks will deliver events out of order and more than once; a log makes that a non-event, and it means the in-flight screen can always be rebuilt exactly as the user saw it.

type TransferEvent =
  | { t: 'quote_accepted';   quoteId: QuoteId }
  | { t: 'onramp_initiated'; ref: ProviderRef; rail: FiatRail }

settlement risk

The funded_held decision

Phase 2 asserted that Corridor holds the payout until ACH clears rather than fronting the funds. This is where that becomes a state, a cost, and an admission.

  • Holding to settlement covers the common returns. R01 insufficient funds and R08 stop payment surface within roughly two banking days. Waiting for settlement before releasing the payout eliminates both — which is precisely why screen 09 shows "USD received" as a discrete, timestamped step instead of hiding a two-day wait inside a spinner.
  • It does not cover R10. An unauthorised-debit return can arrive up to 60 days later. By then the lira has been spent. No holding period that a customer would tolerate closes this window, so it cannot be designed away.
  • So it gets priced and bounded instead. Residual R10 exposure is carried in the $3.75 fee, and constrained by per-user velocity limits until an account has settled history — first transfer capped low, limit rising with successful settlements rather than with elapsed time.
  • The alternative is a real product, not a mistake. Fronting the funds buys same-day delivery and needs working capital plus fraud scoring. It's the right call at scale and the wrong one for a first corridor, and a design doc that pretended the choice didn't exist would be the actual error.

stated plainly

Corridor's ACH exposure is bounded, not eliminated. Anyone operating this for real needs a funded reserve against R10 returns and a written policy for the clawback state. That's a balance-sheet problem wearing an engineering costume, and the honest thing a design document can do is name it and refuse to pretend the state machine solves it.

Idempotency and reconciliation

  • Keys are minted client-side when screen 08 mounts, not at submit. A user who taps through a flaky connection retries with the same key, and the second request returns the first result rather than a second transfer.
  • Provider calls carry the transfer's key, scoped per leg — {transferId}:onramp, {transferId}:payout. A reorg-driven chain resubmit reuses {transferId}:chain, so a duplicate submission is impossible even across process restarts.
  • Webhooks are the fast path; polling is the floor. Any transfer not in a terminal state is re-polled on exponential backoff. Dropped webhooks are normal, not exceptional — a design that only handles the push path is a design that stalls silently in production.
  • Steps are monotonic in the UI. An out-of-order webhook that would move a step backwards is recorded in the log but not reflected on screen 09. A user watching a completed step un-complete has just learned not to trust the screen, and they're right to.
the real leg

Producing the proof artifact

One genuinely real transaction, end to end, signed by a wallet the user owns. Everything else in this build is a simulation and says so; this is the part that isn't. 

// The only place the app itself moves value.
// Privy holds the key shards; the app never sees a private key.

const { wallets } = useEmbeddedEthereumWallet();
const provider = await wallets[0].getProvider();

// ERC-20 transfer(address,uint256) on Base Sepolia USDC
const USDC = '0x036CbD53842c5426634e7929541eC2318f3dCF7e';  // 6 decimals

const txHash = await provider.request({
  method: 'eth_sendTransaction',
  params: [{
    to:   USDC,
    data: encodeFunctionData({
      abi: erc20Abi,
      functionName: 'transfer',
      args: [treasuryAddress, 500_000_000n],   // 500.00 USDC
    }),
  }],
});

// → surfaced on screen 09 the moment it exists, not held back for the receipt.
// → 0x8f2a···c19e  ·  verifiable on sepolia.basescan.org
  • The hash appears mid-flight, not on success. Screen 09 shows it as soon as the transaction is submitted. Proof that is only revealed once everything worked is not proof of much.
  • Testnet is disclosed everywhere it appears — the persistent demo strip on screen 02, and "Base Sepolia" next to the hash on screen 10. A testnet hash presented as mainnet would be the one genuinely dishonest thing in the project.
  • Confirmations are read from the chain, not simulated. The 2 / 12 counter on screen 09 is a real subscription — it's the one number in the whole in-flight screen that nothing could fake.
  • Funded from Circle's public faucet — 20 USDC per address every 2 hours, so the demo amount of 500.00 USDC needs either accumulation across intervals or a smaller headline figure for the recorded walkthrough.

unresolved — needs a decision in phase 4

The locked demo data sends 500.00 USDC, but the faucet issues 20 USDC per 2 hours. Either the walkthrough accumulates a balance over about two days, or the real testnet leg moves a smaller amount than the UI's headline figure. The second option would make the tx hash disagree with the receipt, which defeats its purpose as evidence. Recommendation: accumulate, and record the walkthrough once.

mock strategy

The app cannot tell

A mock that the application knows about is a mock that hides integration bugs until the day you swap it. Corridor's simulated providers implement the same interfaces, emit the same events through the same webhook ingress, and are selected by configuration. 

// providers/registry.ts
const PROVIDERS: Record<ProviderId, Provider> = {
  'bridge.usd.ach':  env.BRIDGE_KEY ? new BridgeOnramp(env)  : new SimulatedOnramp(fixtures.ach),
  'turkey.try.bank': env.TRY_KEY    ? new TurkeyPayout(env)  : new SimulatedPayout(fixtures.try),
  'kyc.fixture':     env.KYC_KEY    ? new VendorKyc(env)     : new SimulatedKyc(fixtures.kyc),
};

// There is no `if (isMock)` anywhere above this line. Not in the orchestrator,
// not in the API layer, and certainly not in the app. The seam is the only
// place that knows, and it decides once, at boot, from the environment.
  • Simulated providers advance on a timer and POST to the real webhook endpoint, signed with a local secret. The ingress path, the signature check, the parseWebhook normalisation, the ordering logic and the reconciler are all exercised identically. When a real key arrives, the untested surface is one adapter.
  • Fixtures encode timing, not just payloads. The ACH fixture settles at T+2 in wall-clock terms, compressed for demos by an env-controlled factor. A mock that returns instantly would have hidden the entire funded_held design.
  • Failure fixtures are first-class. fixtures.try.nameMismatch drives screen 11c end to end — payout rejected, USDC returned to balance, fees for the failed leg refunded. The unhappy paths are exercised on every run, not written once and left to rot.
  • Disclosure is derived, not authored. The demo strip and the per-screen simulated badges read from the same registry that selects the providers, so a screen cannot claim a leg is real while the server is running a simulation. The honesty rule is enforced by construction rather than by remembering.

What has to happen before phase 4

Two of these need an account created by hand. Everything else is code.

Privy app real · self-serve

Create an app at dashboard.privy.io → app ID + client ID. Enable email login and embedded wallets on EVM. Add the Expo scheme to allowed origins. Requires a signup.

Testnet USDC real · self-serve

Fund the wallet from faucet.circle.com on Base Sepolia — 20 USDC per address per 2 hours. Also needs Base Sepolia ETH for gas from a public faucet. Start early — the 500.00 USDC demo figure takes about two days to accumulate.

Bridge sandbox blocked

Requires emailing support@bridge.xyz for a Developer account before an sk-test key can be generated. Worth sending — a reply either way is itself a documentable finding for the writeup. Not on the critical path; the simulated adapter ships regardless.

TRY payout partner simulated

No self-serve option exists for USDC→TRY bank settlement. The adapter is written against a documented partner's API shape and disclosed as simulated. No account needed.

Corridor API code

Quote signing, ledger, webhook ingress, reconciler. Small — the interesting parts are the state fold and the provider registry, not the transport.

Expo app code

@privy-io/expo + native extensions + polyfills. Tokens port from phase 1 unchanged; screens port from phase 2. No web target — Privy's Expo SDK is iOS/Android only, so a web demo is not available as a fallback.
