corridor · failure modes, phase 5

Everything that
goes wrong.

And the one thing no design can fix.

A remittance corridor is a chain of four systems that fail independently, on different timescales, and mostly after the user has stopped looking. This document names each failure, says how Corridor detects it, what the user sees, and, where the honest answer is "nothing", says that instead.

It opens with what is simulated in this build, because a writeup that buried that would have already failed its own test.

disclosure, first

What is not real here

Four of the five rails in this build are simulated. Each is disclosed on-screen at the moment it matters, and the badge text is read from the provider registry rather than written into the screens, so a screen cannot claim a leg is real while a fixture is bound.

Bridge → TRY payoutdoes not exist

Bridge publishes USD (ACH/FedNow/Wire), EUR (SEPA), MXN (SPEI), BRL (Pix), GBP (FPS) and COP. There is no TRY route in either direction. This is not a KYB gate that could be opened; the product is not sold. Phases 1 and 2 named Bridge as the TRY payout provider and were simply wrong; phase 3 caught it against the live route table.

Bridge → USD on-rampsimulated

A real Bridge product, but sandbox access is not self-serve: a Developer account must be granted by Bridge support before an sk-test key can be generated. Modelled on Bridge's documented transfer shape and real ACH timing.

TRY payout partnersimulated

No USDC→TRY bank settlement is available self-serve. The adapter is written against a documented partner's API shape, owns the IBAN validation, and is bound per corridor so a real partner replaces it in one file.

Identity verificationreal flow, fixture verdict

Sequencing, retry, reason-code mapping and the resubmit path are production-shaped. The vendor verdict is a fixture. No documents are captured or transmitted.

The walletsimulated

@privy-io/expo requires native modules and therefore a development build, so the in-app wallet is a fixture and the repo stays runnable with npx expo start. The real Privy adapter binds in the same slot.

The tx hashreal · verified

Discharged. 0x551c···ba10 is a genuine ERC-20 transfer of 1.00 USDC on Base Sepolia, block 45038683, against Circle's canonical contract, produced by scripts/proof.mts and checkable on BaseScan without trusting this repo. The amount differs from the app's 500.00 demo figures because Circle's testnet faucet caps it; the receipt screen states that on the screen itself.

FX rate feedfixed

Pinned at 52.84 TRY/USD. The rate machinery is real (rationals, signed quotes, server-side expiry), but no live feed is attached, so rate-movement failures are modelled rather than observed.

the honest summary

No money moves in this build, and no blockchain transaction exists. What is real is the design, the domain logic, the provider seam, and the failure handling, all of which are exercised on every run because the simulated adapters go through the same ingress, signature check and state fold that a real vendor would.

settlement risk

The 60-day problem

This is the failure that shaped the product. Everything else on this page is engineering; this one is a balance sheet wearing an engineering costume.

  • The shape of it. ACH is pull-based and reversible. Corridor debits the sender's bank, mints USDC, sends it on Base, and a Turkish bank credits lira. The lira is irreversible. The ACH debit is not.
  • Holding to settlement covers the common cases. R01 insufficient funds and R08 stop payment surface within about two banking days. Waiting for settlement before releasing the payout eliminates both, which is exactly why screen 09 shows "USD received" as a discrete, timestamped step rather than hiding a two-day wait inside a spinner.
  • It does not cover R10. An unauthorised-debit return can arrive up to 60 days later. By then the recipient has spent the lira. No holding period a customer would tolerate closes this window.
  • So it is priced, not solved. Residual exposure sits in the $3.75 fee and is bounded by per-user velocity limits that rise with settled history rather than elapsed time. First transfer capped low; limits earned, not aged into.
  • The alternative is a real product, not a mistake. Fronting the funds buys same-day delivery and requires working capital plus fraud scoring. That is the right call at scale and the wrong one for a first corridor.

stated plainly

Anyone operating this for real needs a funded reserve against R10 returns and a written policy for the clawback state. The state machine models the event; it does not pay for it. A design document that implied otherwise would be lying about the only number that could close the business. 

// The distinction the fold has to make, and why `clawback` exists.
// An ACH return before value leaves is a clean refund, and that includes

the payout leg

What Türkiye cannot tell you

Local IBAN validation catches typos, transpositions, wrong-country pastes and bad lengths, all before a network call, on every keystroke. It cannot catch a structurally perfect IBAN belonging to the wrong person, and Türkiye has no name-check service to resolve that.

  • Markets that offer confirmation-of-payee (UK CoP, and increasingly the EU) let you verify the account holder's name before debit. Türkiye does not, so name mismatch is discovered by the receiving bank after the money is already in flight.
  • The design absorbs what it cannot prevent. Warn loudly at entry with the real consequence and the real delay; mark previously-successful recipients verified and default to them; make the returned-payout path non-catastrophic.
  • Screen 11c leads with "Your money is safe" above any explanation, because a user watching ₺26,420 fail needs the location of their funds in the first second, not the third paragraph.
  • The timeline stays visible with the failure in place, so the return reads as a completed round trip rather than a hole. Fees for the leg that did not happen are refunded.

the general rule this is an instance of

When you cannot prevent a failure, make it cheap. Most of the design work on this corridor went into the second half of that sentence.

event delivery

Three clocks, one story

Bridge, the payout partner and the chain all report independently. They will deliver late, twice, and out of order. None of that is exceptional; a design that only handles the happy path stalls silently in production.

  • Push is the fast path, polling is the floor. Any transfer not in a terminal state is re-polled on exponential backoff. Dropped webhooks are expected, not escalated.
  • seq is assigned by Corridor on ingress, never taken from the provider. A vendor's ordering guarantees are that vendor's business.
  • State is a fold over an append-only log. Redelivery is idempotent because duplicates are dropped by event identity, not by seq: a vendor retry passes through ingress again and is assigned a fresh one. Reordering is absorbed rather than corrected: seq is arrival order, so the fold ranks states and a late event describing an earlier moment is logged but never moves the transfer backwards. Both are covered by tests.
  • Steps are monotonic in the UI. A late event that would move a completed step backwards is recorded in the log but not reflected on screen. A user watching a completed step un-complete has just learned not to trust the screen, and they would be right.
  • parseWebhook returns null rather than throwing on unknown or badly-signed payloads. A provider shipping a feature you have not heard of should never be an outage.

at scale

What breaks first

If this corridor took real volume tomorrow, in the order I would expect things to hurt:

  • 1 · Fraud, not engineering. A US-outbound corridor to a high-inflation market is an attractive laundering route. Velocity limits and settled-history tiers are a start; real operation needs transaction monitoring, device fingerprinting and a SAR process. Nothing on the screens hints at how much of this exists behind them, which is correct.
  • 2 · The R10 reserve. Unauthorised-return exposure scales linearly with volume and lands 60 days behind it. Growth makes this worse in a way that feels fine right up until it doesn't.
  • 3 · Payout partner concentration. One Turkish partner is a single point of failure for the entire corridor. The PayoutProvider seam makes a second one cheap to add, which is most of the argument for having built it.
  • 4 · Rate risk on the lock. A 15-minute lock is a free option written to the customer. At volume, in a currency that moves like TRY, that needs hedging or a shorter window.
  • 5 · Reconciliation. Three providers, three clocks, and a ledger that must balance daily against all of them. The event log makes this tractable; it does not make it small.

what this document is claiming

Not that Corridor handles all of the above. It is a case study, and it moves no money. The claim is narrower and, I think, more useful: that the failures were enumerated before the happy path was designed, and that the design visibly changed because of them: funded_held exists because of ACH returns, the PayoutProvider seam exists because Bridge has no TRY route, and screen 11c leads with the location of the money because that is what a frightened user needs first.
